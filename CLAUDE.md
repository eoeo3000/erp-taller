# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"erp-taller" — an ERP for a workshop/service business (Chilean Spanish domain language) that tracks the flow: **Solicitud** (customer request) → **OT** (orden de trabajo / work order, with tasks, Gantt scheduling, materials, financials) → **execution/reports** (field reports with photos, supervisor portal) → **payment**.

Two independent apps in one repo, no shared package/workspace tooling — con **una excepción acotada**: el `package.json` de la raíz existe solo para el tooling de la demo (Playwright y los scripts `demo:*`), porque el grabador recorre las tres apps a la vez y no pertenece a ninguna. No es un workspace: ninguna app resuelve dependencias desde ahí.

Two independent apps in one repo, no shared package/workspace tooling:

- `erp-backend/` — Node.js + Express + Mongoose REST API (CommonJS).
- `erp-web/` — React 19 + Vite SPA (ESM), single-page app with all screens as top-level routes.

They communicate purely over HTTP; `erp-web` talks to `erp-backend` via `VITE_API_URL` (falls back to `http://localhost:5000/api`).

## Commands

### Backend (`erp-backend/`)
```bash
npm start          # node server.js — runs the API on $PORT (default 5000)
```
No hay lint ni build en el backend. `npm run demo:reset` siembra la base de demostración (`scripts/seed-demo.js` + `scripts/datos-demo.js`): datos ficticios, idempotente por wipe+insert, y **aborta si la base conectada no se llama `erp_taller_demo`** — solo lee `MONGO_URI_DEMO`, nunca `MONGO_URI`. Deja los accesos de la demo en `demo-output/acceso-demo.json` (ignorado por git). `npm test` corre `node --test test/*.test.js` — el runner que trae Node, sin framework ni dependencias nuevas; cubre las funciones puras del login (`utils/password.js`, `utils/tokens.js`) el almacenamiento de archivos (`config/almacenamiento.js`, por disco y por bucket contra un S3 falso, más subida/bajada por HTTP real contra los routers de verdad) y los respaldos (`servicios/respaldo.js`, con una base falsa: ida y vuelta de `ObjectId`/fecha/`Decimal128`, retención, y el control de acceso del endpoint), la agenda (`fechasDeTrabajo`, B1), **el gate de `/ots` y `/solicitudes`**, **el registro de talleres** y **el alta de un taller nuevo** (que se instale contra su base y no la del principal, y que un enlace viejo no reinstale un taller que ya opera) (el panel por HTTP y el registro de conexiones con un mongoose falso) (por HTTP contra las tablas de rutas de verdad, con los controladores sustituidos: si alguien agrega una ruta sin gate o con el equivocado, eso se pone rojo), y la configuración que fallaba en silencio (`config/urls.js` con los dos valores reales que rompieron `SPA_URL`, los avisos de `config/mailer.js`, y **qué queda escrito en el log al recuperar una clave** — esa prueba se pone roja si alguien vuelve a registrar el correo completo o el token). **Una prueba no debe dejar que la app escriba en consola**: `node --test` habla con sus procesos hijos por un protocolo binario sobre stdout, y un `console.log` suelto —más aún con emoji, que ocupa varios bytes y puede partirse entre dos trozos— le corrompe el marco cada tantas corridas. Se ve como un fallo intermitente con un error de deserialización que no tiene nada que ver con lo que la prueba verifica (pasó: 1 de cada 5 corridas). Si el código bajo prueba registra algo, capturar `console.log`/`console.error` mientras corre. El frontend usa vitest (`erp-web`, `npm test`).

One-off maintenance scripts live at the backend root and are run directly with `node <file>.js` (not wired into package.json). `test-db.js` is an ad hoc manual check script with a hardcoded local Mongo URI, not a real test. Destructive Mongo cleanup scripts (`borrado_total.js`, `borrarIndice.js`, `limpiar.js`, `limpiarSuministros.js`) live in `scripts/peligrosos/` (see its README) and connect using `MONGO_URI` from `.env` — they now require typing the target database name to confirm before touching anything, but still treat them as dangerous and confirm with the user before running or modifying.

Required `erp-backend/.env` variables: `MONGO_URI`, `PORT` (optional, defaults to 5000), `BREVO_API_KEY` (SMTP relay for outgoing mail), `EMAIL_FROM`. `AUTH_REQUERIDA='true'` activa el login de la SPA (ver `middlewares/sesion.js`) y `IDENTIDAD_REQUERIDA='true'` cierra `/ots` y `/solicitudes` a quien no pruebe quién es (`middlewares/identidad.js`; los dos dejan pasar con un aviso mientras no estén, por el orden de deploy); `SPA_URL` es el host de `erp-web`, usado para armar los links de los correos de recuperación de clave y de invitación **y el enlace de instalación de un taller nuevo**; `SETUP_TOKEN` (opcional) exige esa clave para la primera puesta en marcha. `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` / `R2_BUCKET` mandan las fotos de terreno y los adjuntos a un bucket Cloudflare R2 en vez del disco del contenedor —sin ellas se usa el disco con un aviso por consola, igual que `API_KEY`— y `R2_ENDPOINT` (opcional) apunta a otro servicio compatible con S3; ver [`docs/almacenamiento-archivos.md`](docs/almacenamiento-archivos.md). `MONGO_URI_CONTROL` enciende la **base de control** del multi-taller (etapa 2) y `PANEL_TOKEN` protege `/api/talleres` y, con ella, la página `/panel` —sin cualquiera de las dos esa ruta responde 503, y sin `MONGO_URI_CONTROL` el sistema sigue con un solo taller, el de `MONGO_URI`, exactamente como antes—. `LIMITE_BASE_MB` (512 por omisión, el clúster M0 de Atlas) y `LIMITE_ARCHIVOS_GB` (10, el plan gratuito de R2) son los techos contra los que el panel mide el uso total — **son del clúster y del bucket enteros, no por cliente**; salen del entorno para que al cambiar de plan el panel siga diciendo la verdad. `LIMITE_BASE_AL_PASAR` y `LIMITE_ARCHIVOS_AL_PASAR` (`rompe` por omisión, o `cobra`) dicen **qué pasa al pasarlos**: un M0 lleno deja de aceptar escrituras, pero pasarse de los 10 GB de R2 con el plan pago solo cuesta centavos por GB. Cuál es cuál depende del plan contratado, que el código no puede deducir; por omisión los dos avisan de más, no de menos. `RESPALDO_TOKEN` habilita `/api/respaldos` —**sin ella la ruta responde 503**, al revés que los gates con rollout, porque nace hoy y dejarla abierta regalaría acceso en vez de conservar el estado anterior— y `BREVO_SMTP_USER` mueve al entorno el identificador SMTP que estaba escrito en el código (con el valor anterior como respaldo, para no dejar sin correo a un despliegue que todavía no la defina); ver [`docs/respaldos.md`](docs/respaldos.md). `EMAIL_OPERADOR` (opcional) es adónde llega el **aviso de que un cliente terminó de instalar su taller** (`servicios/avisoInstalacion.js`): **no es una aprobación** —cuando ese correo sale, la persona ya entró— sino el registro de que pasó y cómo se nota lo que de otro modo no se notaría, que el enlace lo usó alguien que no era el destinatario; la vuelta atrás es suspender el taller desde el panel, y el correo lo dice. Va **después** de crear la cuenta, la sesión y consumir el enlace, con su propio `catch`: un Brevo caído no puede ser el motivo de que un cliente nuevo no pueda instalar. Sin la variable no sale nada y no se rompe nada, igual que `EMAIL_REPLY_TO`. En el log va solo el dominio; la dirección completa va en el correo, que es el dato que se quiere saber y va a un buzón. `EMAIL_REPLY_TO` (opcional) es adónde vuelven las respuestas de los clientes: se inyecta como `replyTo` envolviendo el transporte una vez, no en los nueve `sendMail` del proyecto. **`SPA_URL`, `API_URL`, `PWA_*_URL`, `EMAIL_FROM` y la clave de Brevo se revisan al arrancar** (`avisarUrlsInvalidas()` + `mailer.avisarConfiguracion()` en `server.js`): ninguna corta el arranque —el correo roto no debe tumbar el sistema— pero avisan, porque antes una `SPA_URL` mal escrita mandaba correos con links muertos sin una sola queja en el log; ver [`docs/correo.md`](docs/correo.md). Optional: `API_KEY` — shared secret gating the highest-risk write routes (OT, contabilidad, recursos/puestos/calendarios; see `middlewares/apiKey.js`). Unset by default, which leaves those routes unprotected (with a console warning) exactly as before this was added — set it here and set the matching `VITE_API_KEY` in `erp-web/.env` to activate the gate. Not real per-person auth: it ships in the SPA build and is visible in any browser's network tab. `erp-pwa-operativa` also calls one gated route (`PUT /api/ots/:id`, used to save the informe de evaluación **y para marcar tareas como realizadas en S3**) — it needs the same `VITE_API_KEY` set in its own build env too, or that save fails with 401. **Confirmado en la práctica**: sin `erp-pwa-operativa/.env` la app muestra el error pero el flujo se ve normal desde afuera, y la base no recibe nada — se descubrió grabando el video de la demo, donde el informe parecía guardarse y no se guardaba.

## Architecture

### Backend structure
Layered Express app under `erp-backend/src/`:
- `routes/` — one router per resource, all mounted under `/api` in `routes/index.js` (e.g. `/api/recursos`, `/api/ots`, `/api/solicitudes`, `/api/equipos`, `/api/suministros`, `/api/calendarios`, `/api/puestos`, `/api/plantillas`). `server.js` also mounts `/api/mail` (quotation emails) directly, separate from `routes/index.js`.
- `controllers/` — one file per resource, plain `exports.fn = async (req, res) => {...}` handlers. Convention: `try/catch` per handler, `res.status(...).json({ error: ... })` on failure (message key varies: `error`, `mensaje`, `message` — not standardized across the 22 existing controllers, don't assume one). `res.ok(datos, status?)` / `res.fail(status, mensaje)` (`middlewares/respuestas.js`, wired globally in `server.js`) standardize on `{ error }` for failures — use them in new controllers or ones already being touched for another reason, don't retrofit existing untouched controllers just for consistency.
- `models/` — Mongoose schemas. Note the filename casing is inconsistent (`OT.js`, `Recurso.js`, `Solicitud.js`, `Calendario.js`, `Plantilla.js` vs. lowercase `puesto.js`, `suministro.js`, `equiposHerramientas.js`) — match existing require paths exactly.
- `middlewares/auth.js` — trivial shared-secret check (`req.body.key !== "ClaveSecreta123"`), used only on the `webhook-emails` route. Not a general auth system.
- `middlewares/sesion.js` — login de la SPA de escritorio. `identificar` corre sobre toda la API y deja `req.usuario` cuando la request trae `Authorization: Bearer <token>` de una `SesionStaff` válida, sin bloquear a nadie; `requiereSesion` devuelve 401 sin ella. Aplicado en `routes/index.js` a los routers que solo usa `erp-web` (`/data`, `/recursos`, `/equipos`, `/suministros`, `/calendarios`, `/puestos`, `/plantillas`, `/finanzas`, `/contabilidad`, `/import`, `/proveedores`, `/ordenes-compra`, `/disposiciones`, `/demo`, `/clientes`) y a todo `/usuarios` salvo `/whoami`. `/ots` y `/solicitudes` **ya no están abiertos**: usan `requiereIdentidad` ruta por ruta (ver abajo). **Siguen abiertos** `/portal` (el cliente, con su propia `SesionPortal`), `/asignaciones` (la PWA, que comprueba el token dentro de cada controlador), `/uploads`, `/tipos-trabajo` y `/catalogos-transversales`. De esos, el que queda pendiente de verdad es **`POST /uploads`**: cualquiera puede subir archivos al bucket. Igual que `apiKey`, el gate solo bloquea de verdad con `AUTH_REQUERIDA='true'` en el `.env` — sin esa variable deja pasar con un aviso. **`GET /auth/yo` respeta el mismo interruptor**: sin sesión y con el gate apagado responde `200 {usuario: null, authRequerida: false}` en vez de 401, y el SPA entra igual que antes de que existiera el login. Sin eso, desplegar deja a la oficina frente a una pantalla de acceso que nadie puede pasar, porque las cuentas con clave se crean después (`scripts/crearAdmin.js`) — el orden correcto es desplegar, crear la cuenta, y recién ahí activar `AUTH_REQUERIDA`.
- `middlewares/identidad.js` — **quién llama, para las rutas que comparten la oficina y la PWA Operativa**. `/ots` y `/solicitudes` las usan dos clientes con dos pruebas de identidad distintas: erp-web manda `Authorization: Bearer` (sesión de escritorio) y `erp-pwa-operativa` manda el token permanente de la persona en `?token=`. Exigir sesión ahí habría dejado afuera a la PWA, y por eso el router entero estaba sin gate — con el resultado de que **`GET /api/solicitudes` devolvía la cartera completa de clientes a cualquiera que supiera la URL del backend**. `requiereIdentidad` acepta cualquiera de las dos y rechaza al que no trae ninguna; deja `req.usuarioMovil` (nunca `req.usuario`, que significa "sesión de escritorio" — mezclarlos haría que un control de oficina se diera por satisfecho con un token de operario). **No es autorización por recurso**: con identidad válida cualquiera del taller lee cualquier OT. Eso es otro trabajo, por ruta, y el camino ya lo abrió `otController.accionMovil`, que sí exige asignación sobre esa OT. `resolverUsuarioPorToken` vive acá y es **la única definición** — antes había copias en `asignacionController`, `usuarioController.whoami` y `otController.accionMovil`; mismo criterio que `fechasDeTrabajo` tras B1. Desde la etapa 4 **saca el prefijo del taller** del token (en la base está guardado pelado) y **comprueba la pertenencia**: la persona tiene que pertenecer al taller cuya base se abrió, igual que en `sesion.js`. El `taller` es parámetro obligatorio y sin valor por omisión a propósito — uno que se saltara la comprobación sería exactamente el olvido que convierte un sistema multi-cliente en una filtración. El caso que esa comprobación atrapa y la búsqueda por token no: un documento que terminó en la base de otro taller, que es lo que pasa al restaurar el respaldo equivocado.
- Rollout de `IDENTIDAD_REQUERIDA`, en este orden y no en otro: (1) desplegar el backend —el gate avisa y deja pasar—; (2) desplegar `erp-pwa-operativa`, que ahora manda el token en **todas** sus llamadas (va en `conEntorno()`, no en cada función, para que la próxima que alguien agregue nazca identificada); (3) probar en un teléfono de verdad: abrir una OT, guardar un informe; (4) recién ahí poner `IDENTIDAD_REQUERIDA='true'`. Saltarse el orden deja sin guardar su trabajo a un supervisor que esté en terreno con una copia vieja de la app instalada. **`IDENTIDAD_REQUERIDA` exige `AUTH_REQUERIDA` encendida**: sin login el SPA no manda sesión y recibiría 401 en cada pantalla de OT; esa combinación se avisa al arrancar (`identidad.avisarConfiguracion()` en `server.js`) en vez de corregirse sola, porque adivinar cuál de las dos se quiso apagar sería peor.
- `Usuario` es la única tabla de personas y sostiene las dos formas de entrar: `token` permanente (PWA Operativa, sin clave) y `email` + `passwordHash` (escritorio, con sesiones en `SesionStaff`). Ambos campos son opcionales. **Cualquier búsqueda por `token` debe descartar antes el valor vacío**: `findOne({ token })` con token undefined viaja como `{ token: null }` y hace match con los documentos sin ese campo, o sea con las cuentas de oficina.
- Cuentas de escritorio: alta **solo por invitación** desde la app (`cuentasController.js`, rutas `/api/cuentas`, pestaña "Cuentas de oficina" en `BodegaTokensScreen`). No hay registro abierto en la pantalla de ingreso: un correo confirma el buzón, no que la persona trabaje en el taller — quien autoriza es la oficina. Invitar crea el `Usuario` **sin `passwordHash`** (existe pero no sirve para entrar) y manda un link a `/activar?token=`, que reusa `POST /auth/restablecer`: activar una cuenta nueva y reponer una olvidada son el mismo acto (alguien que demuestra tener el buzón elige su clave), solo cambia el texto. Nadie, ni quien invita, conoce la clave de otro. Esas rutas usan `requiereSesionEstricta` y **no** `requiereSesion`: una invitación emitida mientras `AUTH_REQUERIDA` sigue apagada seguiría sirviendo después de encenderla, así que ahí dejar pasar sería regalar acceso permanente. Consecuencia buscada: sin una cuenta previa no se puede invitar desde la app, y la primera sale del script de abajo. Revocar cierra las sesiones abiertas al instante y se deshace con Reactivar (principio de vuelta atrás); nadie puede revocarse a sí mismo, para no dejar al taller sin ninguna cuenta activa. Editar (`PUT /api/cuentas/:id`, botón Editar en la fila): el **nombre** se corrige siempre; el **correo** solo mientras la invitación está Pendiente, porque es con lo que la persona entra —cambiárselo a una cuenta activa la deja afuera al instante y, si el correo nuevo es de otra persona, le entrega el acceso a ella; para eso está invitar al correo correcto y revocar la anterior, que además deja rastro de las dos. Corregir un correo pendiente **reemite la invitación**: el link viejo ya salió al buzón equivocado y seguiría sirviendo, así que emitir otra pisa el `resetHash` y lo mata ahí mismo.
- Primera puesta en marcha (`instalacionController.js`, `POST /api/instalacion`, `InstalacionScreen`): cuando la base no tiene **ninguna** cuenta con `passwordHash`, `GET /auth/yo` responde `{requiereInstalacion: true}` —incluso con `AUTH_REQUERIDA` activa, porque exigir un login que nadie puede pasar solo deja a la oficina afuera— y el SPA ofrece crear la cuenta inicial, que entra de inmediato con su sesión. La ventana se cierra sola: con una cuenta creada el endpoint responde 409 para siempre, sin interruptor que alguien pueda olvidar. `SETUP_TOKEN` en el `.env` la cierra del todo, exigiendo esa clave para instalar. Es además la pantalla que, al pasar a SaaS, se convierte en el registro de cada taller nuevo.
- Alta de un taller nuevo (etapa 3, `servicios/aprovisionamiento.js` + `instalacionController`): quien instala un taller recién dado de alta **no tiene sesión**, y sin sesión `middlewares/entorno.js` resuelve al taller por defecto — sin el enlace, el dueño de un cliente nuevo caería sobre la base del principal. Por eso el slug viaja en el enlace, y **por eso el slug no autoriza nada**: es ruteo, igual que el prefijo del token de sesión. Autorizan tres condiciones juntas: el taller existe y está activo, la clave coincide con `instalacionHash` y no venció, y **ese taller no tiene todavía cuentas de escritorio** — esta última es la que impide que un enlace viejo guardado en un correo sirva para crearse un administrador dentro de un taller que ya opera. El enlace se consume al usarse, vence a los 7 días y se reemite con `POST /api/talleres/:slug/instalacion` (lo que mata el anterior). Clave mala y taller inexistente responden lo mismo, para que esto no sirva de buscador de clientes. **Los índices se construyen antes de crear la cuenta**: en Mongo la base aparece sola al escribir, los índices no —Mongoose los construye perezoso— y sin ellos los once índices únicos del proyecto no existirían en la base nueva, así que dos documentos que chocaran entrarían los dos sin error. La lista de modelos se lee de la carpeta, no a mano. **Sin `taller` en el cuerpo, `POST /api/instalacion` hace exactamente lo de antes.** El slug sale del cuerpo o, si no viene, de la misma pista que mira `GET /auth/yo` (`conexionPedida`): **las dos tienen que resolver el mismo taller**. Cuando no lo hacían pasaba esto, y se veía absurdo desde afuera — `/auth/yo` miraba el taller de la cabecera y decía "falta instalar", el SPA mostraba la pantalla, y al enviarla la instalación caía en el taller por defecto y respondía *"este sistema ya está instalado"*. La pantalla preguntaba por un taller e instalaba en otro. **Un taller que no es el por defecto siempre exige la clave del enlace**, venga el slug de donde venga: si bastara la cabecera, quedarse con el taller de otro sería escribir su identificador. `GET /auth/yo` devuelve además `motivoClaveInstalacion` (`'enlace'` | `'setup'`), porque **son dos claves distintas** —la del enlace de un solo uso, que le llegó al dueño del taller nuevo, y `SETUP_TOKEN`, que es del servidor— y la pantalla no tiene cómo saber cuál corresponde. Antes lo adivinaba mirando si la URL traía `?clave=`, y fallaba justo en el caso más probable: el dueño de un taller nuevo que abre su enlace de **acceso** (`/?taller=x`, que no la trae) en vez del de instalación, y al que la pantalla le decía que buscara un `SETUP_TOKEN` que para él no existe.
- Primer administrador (alternativa por terminal, y salvavidas): `node scripts/crearAdmin.js` con `ADMIN_EMAIL`/`ADMIN_NOMBRE`/`ADMIN_PASSWORD` en el entorno (`--entorno=demo` para la base de demostración, `--reset` para pisar una cuenta existente). Es la única forma de crear la primera cuenta y el salvavidas si se pierde el acceso; no se borra aunque no se use a diario.
- `config/conexiones.js` + `models/Taller.js` + `/api/talleres` — **el registro de talleres** (etapa 2 de [`docs/multi-taller.md`](docs/multi-taller.md)). Las conexiones de producción se abren bajo demanda por taller, se reutilizan y llevan `POOL_MAXIMO`; la demo es **una sola** para todos (§9.2). **`obtenerConexion` sigue síncrona a propósito**: la llama `middlewares/entorno.js` en cada request y buscar el taller en la base de control cada vez agregaría un viaje a Mongo —acá un `findOne` tarda 600-800ms—, así que el registro vive en memoria, se carga al arrancar, se refresca cada minuto y el controlador lo refresca al instante cuando él cambia algo. **Sin `MONGO_URI_CONTROL` nada de esto se nota**: un taller, el de `MONGO_URI`. Al encenderla por primera vez el taller existente se anota solo, o el despliegue siguiente respondería "Taller desconocido: principal" a todos. Tres cortes con prueba: dos talleres no pueden compartir base (un copiar-y-pegar al dar de alta bastaría para que uno viera los datos del otro), un taller suspendido o de baja **no obtiene conexión** (el corte está en el registro, no en los controladores, así que ninguna ruta nueva puede olvidarlo), y si a un taller le cambian la base **se cierra la conexión anterior** (seguir usándola sería escribir en la base vieja tras la mudanza). La `mongoUri` **nunca sale por la API**: es una credencial. **`resolverTaller` vive acá y es la única definición** — había una copia congelada en `config/talleres.js` que solo conocía `principal`, así que durante dos etapas un token con el prefijo de otro taller caía en la base del principal y dejaba a esa persona afuera sin un solo error. Si se agrega otra forma de preguntar "¿existe este taller?", se repite el mismo bug.
- **Entrar a un taller que no es el principal** (`middlewares/entorno.js` → `conexionPedida`, usado por `authController`). Entrar, recuperar la clave y activar una invitación ocurren **sin sesión**, así que el taller no puede salir del prefijo del token: `resolverEntorno` los mandaba al taller por defecto y el correo de alguien de otro taller se buscaba donde no estaba — no podía entrar nunca. La salida es la misma que ya usan el prefijo y el enlace de instalación: **el slug viaja como pista (`X-Taller` o `?taller=`) y no autoriza nada**, porque esas rutas exigen una credencial que tiene que existir *en esa base*. Tres candados: **solo sin sesión** (con `req.usuario` manda el prefijo, o cualquiera con cuenta saltaría a otra base por cabecera), solo talleres registrados y activos, y **nunca lanza** (un slug desconocido cae en la base por defecto, donde la credencial tampoco valida — responder distinto lo convertiría en un buscador de qué clientes existen). **No vive dentro de `resolverEntorno` a propósito**: si la cabecera eligiera la base para toda la API, las rutas que siguen abiertas (catálogos, tipos de trabajo) servirían las de otro taller. Del lado del SPA lo recuerda `erp-web/src/utils/taller.js`, que lee `?taller=` del link una vez y lo propaga por `axios.defaults`; los links de recuperación e invitación ahora lo llevan. **Son DOS memorias, y esa es la parte que no es evidente**: la pista de un link va en `sessionStorage` (esta pestaña y nada más) y la del navegador en `localStorage`, que **solo escribe entrar**, con el prefijo del token. Empezó siendo una sola en `localStorage` y rompía a quien administra varios clientes: `localStorage` es del ORIGEN, no de la pestaña, así que apretar «Abrir» en el panel para mirar la puerta de un cliente dejaba **todo** el navegador apuntando ahí —todas las pestañas, y al día siguiente también—, y desde entonces su propio correo se buscaba en la base de ese cliente y su clave correcta fallaba con «Correo o clave incorrectos», que describe otra cosa. Visitar a sus clientes lo dejaba afuera de lo suyo. Lo único que se pierde con la división: quien abre su link, no entra y cierra el navegador necesita el link otra vez — sin haber entrado no podía hacer nada igual, y con entrar una sola vez la memoria durable queda puesta. **Entrar corrige la pista**: `fijarSesion` toma el taller del prefijo del token, que es la autoridad. Sin eso, abrir una vez el enlace de instalación de un cliente deja ese navegador apuntando a su taller para siempre — quien administra visita varios enlaces y después no puede volver a entrar al suyo. **Pero eso ocurre DESPUÉS de entrar, que es justo lo que ahí no se puede hacer**: con la pista apuntando a otro cliente, el correo se busca en esa base, no está, y el backend responde «Correo o clave incorrectos» — correcto de su lado, porque distinguirlo diría qué correos existen en qué cliente, pero describe mal lo que pasó: la clave estaba bien, la base no. Pasó en producción. Por eso la salida está en la pantalla de ingreso: **tras un error**, y solo entonces, dice a qué taller está entrando este navegador y ofrece `olvidarTaller()` (`utils/taller.js`), que lo devuelve al taller por defecto. Mostrarlo siempre invitaría a tocarlo a quien no tiene ningún problema, y el slug no es un secreto: lo guardó este mismo navegador. Las tres funciones van envueltas en `try/catch` porque el módulo se importa al arrancar el SPA y en una ventana privada `localStorage` lanza — sin eso, lo que se ve no es un aviso sino una pantalla en blanco.
- **El panel de talleres** (`GET /panel`, `src/paneles/panel.html` + `servicios/metricasTaller.js` + `GET /api/talleres/metricas`). Es la herramienta de quien arrienda el sistema, no la de ningún taller: lista los clientes, qué tan recientemente los usaron, cuántas OT/solicitudes/cuentas tienen y si su base responde. Se monta **fuera de `/api`**, igual que `/uploads`, porque es una página. **La página es pública y no trae ni un dato**: es un formulario y el código que pinta la tabla; todo lo que muestra lo pide después a `/api/talleres*` con `PANEL_TOKEN` en una cabecera. Así la clave **nunca viaja en la dirección** —una URL con la clave adentro queda en el historial, en los logs y en el `Referer`— y no hace falta inventarle una sesión al panel. Sin recursos externos (ni tipografías ni librerías): un panel que depende de un CDN deja de verse el día que ese CDN falla. Tres cosas que tienen prueba y no son evidentes: **una base caída se marca en su fila en vez de tumbar la consulta entera** (enterarse de eso es justamente para lo que existe el panel, así que no puede ser lo primero que se rompe), un taller **suspendido** se distingue de uno caído (`baseResponde: null`, no `false` — es una decisión comercial, no un problema técnico), y la actividad mira **las dos puertas** (`ultimoAccesoSpa` del escritorio y `ultimoAcceso` de la PWA), porque un taller donde solo trabajan los supervisores desde el teléfono se vería muerto mirando una sola. **Dar de alta un cliente es escribir su nombre**: el identificador se deriva del nombre (acentos reducidos, no borrados — si no, "Montaña" quedaría "montaa") y la cadena de conexión se deriva de la del propio servidor cambiándole el nombre de la base (`servicios/baseDelTaller.js`). Eso saca el paso más peligroso del alta —pegar una `mongoUri` a mano, donde un error de copiado deja a **dos clientes compartiendo base**— y el único que obligaba a salir del panel. Se puede mandar una `mongoUri` explícita igual: es el caso de §9.1, mover a un cliente que creció a su propio clúster. **La derivación se hace cortando la cadena a mano y no con `new URL()`**: una `mongodb://` con varios hosts (un replica set escrito a mano) no parsea, y ahí se caería el alta. Los parámetros (`retryWrites`, `w=majority`, `appName`) se conservan enteros — perderlos cambia cómo se conecta, y en silencio. **Cada fila ofrece el enlace que sirve, y solo ese**: un taller que ya opera, el de acceso (`SPA_URL/?taller=<slug>` — el `?taller=` es lo que hace que el correo de esa persona se busque en SU base, sin él no puede entrar); uno que **todavía no tiene cuentas**, el de instalación, que lleva la clave adentro. El de acceso **no se le ofrece a un taller sin instalar**, y esto pasó de verdad: se comparte, el dueño cae en la pantalla de instalación con el campo vacío, y ahí no hay nada que pueda escribir —la clave no se recupera, solo se reemite—. El botón se llama «Enlace de instalación» y no «Reemitir»: la primera vez que se necesita, nadie está reemitiendo nada, está buscando qué mandarle al cliente. Un taller que ya opera no necesita ese enlace nunca más y el backend lo rechaza con 409: ofrecer un botón que va a fallar es peor que no ofrecerlo. La decisión mira `cuentas`, la misma definición que usa el backend para saber si una instalación sigue abierta, así los dos lados no pueden contradecirse. Reemitir **pregunta antes**, porque mata el enlace anterior — que puede estar ya en el correo del cliente. El host sale de `spaUrl` en la respuesta del servidor y no escrito en la página: si estuviera escrito, el día que cambie `SPA_URL` el panel seguiría dando el link viejo sin que nadie lo note. **Cada fila entra al taller y edita su marca.** «Abrir» lleva a la puerta de ese cliente (`SPA_URL/?taller=<slug>`, en una pestaña con `noopener` — sin él esa pestaña puede cambiar la dirección de la del panel, que es la que guarda `PANEL_TOKEN`) y **no entra**: la clave del panel no es una cuenta en la base del taller, y que no se pueda entrar a mirar los datos de un cliente es una propiedad del diseño, no algo que falte. «Marca» edita lo que ve la gente de ese taller: **el nombre que muestra su app y el logo que sale en su cotización** (`Taller.marca`, `servicios/marcaTaller.js`). Tres decisiones con prueba: el nombre de la marca **no es `Taller.nombre`** —ese es cómo se llama al cliente en el panel; si fueran el mismo campo, desplegar esto habría cambiado el encabezado de la app de «Taller ERP» a «Taller principal» sin que nadie lo pidiera, y vacío significa «la app usa el nombre de siempre»—; el logo se guarda **como data URI en la base de control** y no en el bucket (los archivos de R2 todavía no están separados por cliente, etapa 5, y el destino del logo es `jsPDF.addImage`, que solo acepta data URI), con un tope de 150 KB porque viaja en cada respuesta del panel y en cada arranque del SPA; y **solo PNG y JPEG** — un WEBP se vería bien en el panel y en la app y recién fallaría al generar una cotización, que es el peor momento para enterarse. La página reduce la imagen a 600px antes de subirla, así que el tope nunca se topa con el archivo original. **La marca viaja en las cuatro respuestas de `GET /auth/yo`, incluida la de 401**: esa es la que hace aparecer la pantalla de ingreso, donde más se ve. Sale del registro en memoria (`marcaDeTaller` en `config/conexiones.js`), así que no agrega un viaje a Mongo. Revela el nombre que un taller eligió mostrar para un slug que hay que acertar, y el slug se deriva del nombre: acertarlo ya implica conocerlo. En pantalla van **el logo arriba y el nombre debajo**. Primero se probó mostrando solo el logo, porque los cuatro lugares donde aparece son angostos —el menú mide 186px y la tarjeta de ingreso 328px— y uno al lado del otro el nombre salía cortado («MAEST…»). Con la app andando se vio que así falta: el logo solo deja la pantalla sin decir de quién es, que es lo que esto tiene que contestar. Apilados caben los dos, y el nombre **envuelve en vez de truncarse** —en dos líneas se lee, con puntos suspensivos no—. El logo va sobre un recuadro blanco porque las cuatro bandas donde se muestra son casi negras y un logo de tinta oscura ahí no se lee; la cotización muestra los dos también, que ahí el ancho sobra y en un papel que va a un cliente la razón social no es decoración. **Sin marca el PDF sale exactamente como antes**: `dibujarMarcaPdf` devuelve 0 y el desplazo de todo el encabezado es 0 — poner «Taller ERP» en una cotización sería escribir el nombre del software en el papel del taller. De paso: la celda de la columna **Base nunca se pintaba** (el `<th>` estaba y la función también, pero la fila no la llamaba), así que todo salía corrido una columna y lo que se perdía era justo si la base del cliente responde. Hay una prueba que cuenta `<th>` contra `<td>`. **Desde la etapa 5 el panel mide por cliente**: cuántos archivos tiene, cuánto ocupan y cuándo fue su último respaldo (verde el mismo día, ámbar hasta tres, rojo después; «nunca» en rojo). Las dos mediciones —base y almacén— van en paralelo y son independientes: la base de un taller puede estar caída con su bucket intacto, y los archivos y el último respaldo de ese cliente son justo lo que se quiere mirar en ese momento. **Uso total, contra el techo del plan** (`servicios/limites.js`): cada fila dice además cuánto ocupa su base (`dbStats`, **`dataSize` y no `storageSize`**: es el número que Atlas compara contra el tope en su propia pantalla, «Data size: X / 512 MB». La diferencia no es cosmética — WiredTiger comprime, así que `storageSize` suele ser bastante menor, y medirlo haría que el panel diga «te queda espacio» justo cuando Atlas ya no deja escribir), y una tarjeta suma todo contra `LIMITE_BASE_MB`/`LIMITE_ARCHIVOS_GB`. **La suma es lo que no se puede deducir mirando fila por fila**: los topes de Atlas y de R2 son del clúster y del bucket enteros, así que un taller en verde no dice nada si entre todos ya se llenó; por eso el total incluye también la base de control, la demo y los respaldos. **El rojo está reservado para lo que se rompe.** Un tope de los que rompen va verde hasta 70%, ámbar hasta 90 y rojo después (ámbar en 90 y no en 95 porque entre que se nota y que se cambia de plan pasan días). Uno de los que **cobran** va verde hasta el 100 y ámbar después: antes de cruzarlo no pasa nada, así que avisar al 70% sería ruido, y cruzarlo tampoco es una emergencia. Pintarlos igual entrena a ignorar el rojo — la primera vez que el rojo resulta ser «te van a cobrar 20 centavos», el rojo dejó de significar algo. Cada línea dice en palabras qué pasa al pasar su tope, así que el color no es lo único que lo explica. **Esto mide y NO corta, a propósito**: lo que se subiría al tope son las fotos de evidencia, y rechazarlas dejaría a un supervisor en terreno sin poder guardar su trabajo; si alguna vez hace falta cortar, la regla es avisar mucho antes y nunca bloquear la evidencia de un trabajo en curso. El tamaño de la base se mide **con su propio `catch`**: es un dato de gestión, no una señal de salud, y si `dbStats` no estuviera disponible en algún plan un taller sano quedaría marcado como caído. Lo único que el panel todavía dice en vez de mostrar es **cuántos archivos quedan sin separar por taller**: mientras queden, la cuenta de cada uno está incompleta, y un número incompleto que se ve completo es peor que ninguno.
- **El probador de las apps móviles** (`GET /moviles`, `src/paneles/moviles.html` + `routes/movilesRoutes.js`). Los dos teléfonos en una pantalla —el de terreno y el del cliente— al tamaño de un teléfono de verdad, con presets, rotar, recargar y elegir entorno. Existe porque probar un flujo que cruza las dos apps (el supervisor cierra el trabajo, el cliente lo ve) obligaba a tener dos aparatos a mano o a cambiar de pestaña perdiendo de vista una. **No habla con la API ni pide ninguna clave**: los links los pega quien prueba, con el token que ya tiene. Eso es deliberado — los tokens son credenciales y `usuarioController.listar` los esconde a propósito (`.select('-token')`), así que una página que los fuera a buscar al servidor sería un agujero abierto para ahorrarse un pegado; hay prueba de que no llama a `/api/`. Se recuerdan en **sessionStorage**, no en localStorage: llevan un acceso permanente adentro. El marco se abre con `allow="camera; geolocation"` porque un iframe se las niega por omisión y la PWA Operativa —cuyo corazón son las fotos de evidencia— fallaría sin decir por qué. Las direcciones configuradas de cada app se inyectan **serializadas con `JSON.stringify`** y no pegadas como texto: una comilla en una variable de entorno rompería el script entero y el síntoma sería un probador en blanco, sin nada que apunte al `.env`. Dos cosas que la página dice en pantalla porque confunden: **la sesión de adentro no es la de afuera** (el navegador guarda aparte el almacenamiento de una página incrustada, así que entrar en el marco no deja entrado en la pestaña) y **un teléfono en blanco significa que ese servidor no permite incrustarlo**, no que la app esté rota — para eso está «Abrir aparte».
- `config/almacenamiento.js` — dónde viven los archivos que se guardan para siempre (fotos de evidencia, adjuntos de solicitudes). Bucket **Cloudflare R2** si están las variables `R2_*`, disco local si no, y al leer se intenta el bucket y después el disco —así lo subido antes de encender R2 se sigue sirviendo mientras se migra (`scripts/migrarArchivosAR2.js`). **El disco de Render es efímero**: se borra en cada deploy, y por eso las fotos de terreno desaparecían solas dejando la URL apuntando a nada. **La forma de la URL no se toca**: se guarda `/uploads/<clave>` y el backend sirve esa ruta desde el bucket, porque `erp-web/src/utils/fotos.js` y `erp-pwa-operativa/src/api.js` arman la absoluta con `BACKEND_ORIGIN + data.url` y hay miles de URL viejas ya escritas en la base. El bucket queda **privado** (son fotos de instalaciones de clientes); las lecturas pasan por `routes/archivosRoutes.js`, montado en `/uploads` fuera de `/api`. **Desde la etapa 5 cada taller tiene su carpeta**: `talleres/<slug>/<archivo>` (y `demo/<archivo>`, aparte, porque la demo es una sola para todos y sus archivos de prueba no pueden contar en la medición de un cliente real). El taller sale de la request (`req.taller`), nunca del cuerpo ni de la URL, y **si no viene `guardar()` lanza** en vez de escribir en la raíz: una ruta de subida nueva que se olvide de pasarlo tiene que romperse de inmediato, no acumular archivos sin dueño durante meses. Que la carpeta aparezca en la URL **no autoriza nada**: `/uploads` sigue abierto igual que antes y para leer una foto hay que saber su nombre (marca de tiempo + número al azar); separar por taller es para respaldar, medir y borrar por cliente. **La lectura entiende las dos formas** —si la clave suelta no está donde dice la URL se busca dentro del taller principal, que era el único que existía cuando esas URL se escribieron— y `scripts/migrarArchivosPorTaller.js` mueve los que quedaron sueltos (copia, verifica, y recién entonces borra; sin `--hacerlo` solo muestra qué haría) **sin tocar ni una URL de la base**. `archivosRoutes` monta tres rutas explícitas y ningún comodín: con parámetros separados ninguno puede contener una barra, así que no hay forma de escaparse de la carpeta.
- `middlewares/demoSoloLectura.js` — con el entorno demo activo rechaza con 403 **cualquier `DELETE`** de la API (montado en `server.js` justo después de `resolverEntorno`). Bloquea por verbo y no por lista de rutas, así una ruta de borrado nueva queda cubierta sola. `erp-web` hace lo propio del lado del cliente: `App.jsx` envuelve todos los `eliminarX` en un solo lugar (`sinBorrarEnDemo`) para que la persona lea una explicación en vez de un error.
- `middlewares/upload.js` — multer **en memoria** con límite de 12MB (antes: disco, sin límite), compartido por `uploadRoutes` y `solicitudRoutes`; el buffer se lo lleva `almacenamiento.guardar()`. `importExportRoutes` tiene su propio multer en memoria para los Excel, que se leen y se botan: no pasa por el almacenamiento.
- `servicios/respaldo.js` + `controllers/respaldoController.js` (`/api/respaldos`) — respaldo y restauración de la base al mismo bucket R2, **uno por taller** bajo `respaldos/produccion/<taller>/` (la demo sin dividir, que es una sola), conservando los 30 más recientes **de cada uno** — con una sola lista compartida, treinta respaldos del cliente grande empujarían fuera todos los del chico. `POST /api/respaldos` sin `?taller=` recorre **todos los activos**, leyendo la lista del registro y no de una constante: así el cliente que entre mañana se respalda solo. Un taller que falla no corta la vuelta y la respuesta dice cuál fue. El archivo guarda **de qué taller salió**, que es lo que permite que `restaurar.js` avise antes de meterle a un cliente los datos de otro; los respaldos anteriores a la etapa 5 no traen ese campo, se entienden del principal y **cuentan para su retención**, así que la poda se los lleva sola en vez de dejarlos envejecer para siempre. Los scripts resuelven la base por el registro (`scripts/_conexion.js`) y no por `MONGO_URI`: si la clave se armara con el taller del argumento y la lectura con la base del `.env`, un `--taller=rivas` guardaría los datos del principal bajo el nombre de Rivas, y el archivo se restauraría sin un solo error. `--listar` no abre ninguna conexión, que es justo lo que se necesita cuando Mongo no responde. **Se serializa con EJSON canónico y no con `JSON.stringify`**: este último convierte un `ObjectId` en `{}` y una fecha en texto, así que el respaldo se crearía sin error y al restaurar rompería el vínculo `OT.solicitudId` → `Solicitud` y degradaría los `Decimal128` de los totales — hay pruebas para los tres casos. Lo dispara `.github/workflows/respaldo.yml` a diario, y no un temporizador interno, porque en el plan gratis de Render el servicio se duerme y un `setInterval` no correría. A mano: `node scripts/respaldo.js`; restaurar: `node scripts/peligrosos/restaurar.js` (pide el nombre de la base y guarda un respaldo del estado actual antes de pisar nada). Ver [`docs/respaldos.md`](docs/respaldos.md).
- `config/mailer.js` — nodemailer transporter via Brevo SMTP relay, used for quotation emails and supervisor-portal notifications. **No registrar nunca el valor de `BREVO_API_KEY`, ni truncado**: había un `console.log` con sus primeros caracteres en cada arranque, y los logs de Render quedan guardados y los lee cualquiera con acceso al panel. `revisarConfiguracion(env)` devuelve la lista de problemas en vez de imprimirla, para poder probarla sin abrir una conexión SMTP; `avisarConfiguracion()` es la que imprime y la llama `server.js`.
- **Diagnosticar el correo** ([`docs/correo.md`](docs/correo.md)): la recuperación de clave responde lo mismo exista o no la cuenta —si no, el formulario sirve para averiguar qué correos están registrados— así que el diagnóstico va al log con `[auth] recuperación: <qué pasó> (@dominio, taller <slug>)`, **seis** casos distinguibles. **Solo el dominio, nunca la dirección completa ni el token de reset**: el log de Render lo lee cualquiera con acceso al panel, la parte local dejaría ahí la lista de quién tiene cuenta y el token es una credencial viva por 60 minutos. **Y el taller**, porque sin él la línea más común —«ninguna cuenta con ese correo»— no se puede interpretar: recuperar pasa **sin sesión**, así que la base sale de la pista del navegador (`conexionPedida`), y si esa pista apunta al cliente equivocado el log dice exactamente lo mismo que si la cuenta no existiera. El slug no abre nada, y es lo único que distingue «este correo no tiene cuenta» de «buscamos en la base equivocada». **Quiénes pueden entrar, y a qué taller** (`GET /api/talleres/cuentas`, tarjeta «Cuentas» del panel y botón por fila): la misma pregunta de soporte, sin entrar al servidor. Busca por parte del correo o del nombre —el caso real no siempre es «¿está este correo?» sino «no me acuerdo con cuál la creé»— y el filtro se aplica **en memoria y no con un `$regex`** armado con lo que alguien escribe, que es una forma conocida de colgar una base. Cada fila dice además **si alguna vez entró** (`ultimoAccesoSpa`) y **cuándo se creó** (`timestamps`): una invitación que nunca se activó y una cuenta que se usó y se rompió se ven idénticas sin eso, y «creo que yo sí había entrado con esa cuenta» es lo primero que se piensa — una fecha lo cierra, una opinión no. La de creación descarta de una lo otro que se sospecha enseguida, que algo la haya borrado. **Y cada fila actúa**: reenviar la invitación, revocar y reactivar, contra la base de ese taller (`POST /api/talleres/:slug/cuentas/:id/{reenviar,revocar,reactivar}`). Hacen falta porque quien arrienda **no tiene cuenta dentro de la app de sus clientes** —y que no la tenga es del diseño—, así que no podía ayudar a alguien de otro taller que quedó con su invitación sin activar. **Las tres son reversibles, y eso decide cuáles existen**: reenviar emite otro link y mata el anterior, revocar se deshace con reactivar. **Borrar no está y no va a estar**: es irreversible y borrar la última cuenta de un taller haría que `GET /auth/yo` vuelva a responder `requiereInstalacion`, o sea **reabriría la ventana de instalación de ese cliente**; hay prueba de que la página no ofrezca un borrado. La lógica vive en `servicios/cuentasDeTaller.js` y **es la misma que usa la app** (`cuentasController` delega ahí): dos copias se habrían separado a la primera corrección, como ya pasó con `fechasDeTrabajo`. Dos candados con prueba: **no se revoca la única cuenta que puede entrar** —desde la app alcanzaba «nadie se revoca a sí mismo», porque quien revoca es una de ellas; desde el panel no hay un «sí mismo» y dejar al cliente sin ninguna exige entrar al servidor a correr `crearAdmin.js`— y una invitación sin activar **no cuenta** como cuenta que puede entrar, o el candado se abriría solo invitando a alguien que nunca va a activar. Y **no se reenvía a una cuenta revocada**: `POST /auth/restablecer` exige `estado: 'activo'`, así que ese link nacería muerto — el corte está en el servicio y no solo en el botón. **Dónde está el límite**: quien administra sigue sin poder mirar los datos de un cliente —sus OT, sus precios— y esto muestra quién puede entrar, que es infraestructura y es lo que hace falta para sostenerlo. Pero **ensancha lo que vale `PANEL_TOKEN`**: perderla ahora expone también los correos de la gente de cada taller, datos personales de terceros; de ahí las tres reglas con prueba —nunca **sale** `passwordHash`, `token` ni `resetHash` (el token de la PWA entra sin clave), pero **`passwordHash` sí se TRAE de la base**: excluirlo en la consulta parecía lo prudente y fue un error grave, porque `resumen()` lo lee para decidir `puedeEntrar` e `invitacionSinActivar` — sin el campo, el panel mostraba **todas** las cuentas como «invitación sin activar», incluidas las que entran todos los días, y se buscó durante días el problema de una cuenta que estaba perfectamente bien. Lo que impide que el hash salga no es la consulta sino `resumen()`, que nombra sus campos uno por uno. Las pruebas no lo vieron porque el doble **ignoraba `select()`**; ahora lo honra, que es la única forma de que una consulta que se lleva un campo de más o de menos se note; solo cuentas **con correo**, porque un `Usuario` con solo token es alguien de terreno; y un taller caído o suspendido **se nombra** en vez de desaparecer, porque contestar «no está» con una base sin revisar manda a invitar una cuenta que ya existe—. **Y trajo el primer texto de terceros a la página**: hasta acá todo lo que el panel pintaba lo había escrito quien administra, y los nombres de las cuentas los escribe la gente de cada taller en su propia app. Esta página guarda `PANEL_TOKEN` en su `sessionStorage`, así que un nombre con una etiqueta adentro se la llevaría, y a quien lo pusiera le bastaría una cuenta en su propio taller: por eso existe `seguro()` y hay prueba de que `filaCuenta` no use `texto()` para nada que venga de la API. **Cuando el log no alcanza** —dice «ninguna cuenta con ese correo en este taller» y quedan dos explicaciones que se arreglan distinto, que no exista o que esté en OTRO taller mientras ese navegador apunta al principal— está `node scripts/buscarCuenta.js correo@x` (`servicios/buscarCuenta.js`): recorre los talleres y dice en cuál está, en qué estado, y **qué hacer** —invitar, mandar el enlace `?taller=<slug>` de su taller, reenviar la invitación, o mirar el envío—. **Nunca va por HTTP**: preguntar «¿en qué cliente está este correo?» desde afuera convierte cualquier formulario en un buscador de a qué taller pertenece cada persona, que es justo lo que la respuesta única de la recuperación existe para impedir; desde un script las credenciales ya están en la mano y no agrega ningún acceso. Nunca devuelve el `passwordHash` ni el `token` de la PWA —esto se pega en un chat— y una base caída no corta la vuelta pero **marca la respuesta como incompleta**: decir «no existe» con un taller sin revisar manda a invitar una cuenta que ya existe. La sexta: una cuenta **revocada** ya no se confunde con una que no existe —antes daban la misma línea y mandan a lugares distintos: una a revisar el correo o el taller, la otra a reactivarla en Cuentas de oficina—; la consulta extra solo ocurre en el camino que ya falló. Hay pruebas de las cuatro reglas.

**`GET /api/data`** (`dataController.getAllData`) is the primary sync endpoint: it fetches all collections (calendarios, equipos, ots, recursos, solicitudes, suministros, puestos, plantillas) in parallel and returns them as one payload. The frontend polls this endpoint (see below) rather than using per-resource fetches for its main data load.

**Domain flow / model relationships:**
- `Solicitud` (customer request, `estado` starts `'Pendiente'`) is converted into an `OT` via `otController.convertirOT` / `actualizarOT`, which upserts an `OT` document reusing the `Solicitud`'s `_id` as `solicitudId` and auto-generates `numeroOT` in the form `OT-2026-0001` (sequence scoped to the hardcoded year prefix `OT-2026-`). Deleting an `OT` resets its linked `Solicitud` back to `'Pendiente'`.
- `OT` embeds its own working data: `tareas` (scheduled tasks, each with `operarioId`/`operarioNombre` as **arrays**, supports multiple assignees), `componentes` (materials/equipment line items), `logistica` (transport line items), `reportes` (field reports with photo/comment, used by the field-report and supervisor-portal flows), `pago` (payment status subdocument), and `granTotal`.
- `Recurso` = personnel/human resource, referencing `Calendario` (a work-schedule template: weekly or rotating `tipo: 'rotativo'` shift cycles with per-day time blocks) via `calendarioId`, plus per-date manual overrides in `ajustes` (a `Map<dateISO, hours>`). Deleting a `Recurso` or `Calendario` cascades a cleanup pass over all `OT.tareas` (via `updateMany`/`arrayFilters`) so the Gantt doesn't reference dangling operarios.
- **Qué trabajo ve cada persona cada día** lo decide `asignacionController.fechasDeTrabajo(ot)`, y **es la única definición**: todo lo que conteste "¿qué le toca a esta persona tal día?" tiene que pasar por ahí (Mi día, Mi semana y los contadores de Mi panel en la PWA Operativa). Las tareas mandan (`OT.tareas[].fecha`); `OT.fechaEjecucion` es una fecha de cabecera y solo vale de respaldo cuando no hay ninguna tarea con fecha — **no se suma** a las de las tareas, porque se escribe a mano desde Antecedentes sin tocar `tareas[]` y puede apuntar a un día vacío. Había tres versiones de este cálculo que se contradecían entre sí (ver B1 en [`docs/bugs-conocidos.md`](docs/bugs-conocidos.md)): no agregar una cuarta.
- **Bodega y estados de la OT** (`otController.aplicarReservaPorCambioEstado`, llamado desde `actualizarOT`, `aplicarRespuestaCotizacion` y `accionMovil`): `Planificada→Programada` reserva (`stockReservado` sube, equipos a `Reservado`); entrar a `En Ejecución` pasa los equipos a `En Uso`; `Trabajo Terminado` libera la reserva **y consume el material** (`stockActual` baja, movimiento `Salida`); reabrir (`accion: 'reabrir'`) revierte las dos cosas. Cada tramo deja línea en `OT.bitacora` con autor `Sistema`. `stockActual` también se mueve al recibir una orden de compra y por ajuste manual, y por nada más.
- `Puesto` = job role with an hourly cost (`costoHora`), referenced by name (not by `_id`) inside `OT.tareas[].puesto`.
- `Plantilla` = a reusable task/material template that gets applied when building out an `OT`.
- `EquiposHerramientas` and `Suministro` are separate catalogs (tools/machinery vs. consumable supplies), both flow into `OT.componentes` when used on a work order.
- **Supervisor portal** (`otController.js`, functions `enviarAlSupervisor` / `supervisorPortal` / `supervisorAccion`): generates a random `tokenEjecucion` stored on the `OT`, emails a link containing it, and serves a server-rendered HTML page (no auth beyond token match: `ot.tokenEjecucion !== token` → 403) that lets a supervisor start/pause/report/finish work without a login. Treat this token as the only access control on that flow — do not assume real authentication exists there. A newer, per-person token flow exists in parallel for the PWA Operativa (`Usuario`/`Asignacion` models, `otController.accionMovil`, see `docs/estrategia-movil.md`) — this older per-OT flow stays alive only until every outstanding `tokenEjecucion` link has been used/expired and the SPA gets an admin screen to create `Usuario`/`Asignacion`; don't assume it's dead code.

### Frontend structure
`erp-web/src/App.jsx` is the composition root: it owns **all** application state (recursos, ots, solicitudes, calendarios, componentes, suministros, puestos, plantillas) via `useState`, defines every CRUD/mutation function (e.g. `crearRecurso`, `actualizarOtGlobal`, `guardarCalendarioGlobal`, `crearPuesto`, `enviarASupervisor`), and passes both state and handlers down as props to screen components — there is no context provider, Redux, or React Query; **all cross-screen data lives in `App.jsx` and flows down via props**. When adding a feature that needs new server data or mutations, add the fetch/state/handler in `App.jsx` and thread it through as a prop, following the existing naming pattern (`crearX`, `actualizarX`, `eliminarX`, `...Global`).

Data freshness: `App.jsx` fetches `/api/data` once on mount and then polls it every 30s, doing a `JSON.stringify` diff per slice before calling the corresponding setter (`syncState` helper) to avoid unnecessary re-renders. El poll manda `headerSondeo()` (`X-Sondeo: 1`) para que el backend no cuente esa llamada como actividad de la persona — si no, una pestaña abierta mantendría la sesión viva para siempre.

Acceso: `App.jsx` pregunta a `GET /api/auth/yo` al montar y guarda el resultado en `acceso` (`'verificando' | 'requiere-login' | 'adentro'`). Solo con `'requiere-login'` — es decir, cuando el backend respondió 401 porque `AUTH_REQUERIDA` está activa — renderiza `LoginScreen` en vez del router; con el gate apagado entra sin sesión y sin bloque de usuario en el nav — salvo en las rutas de `RUTAS_PUBLICAS` (`/portal`, el link que se manda a los clientes por WhatsApp, y `/restablecer`, el del correo de recuperación), que se montan solas sin el shell. `utils/sesion.js` guarda el token en **sessionStorage** (muere al cerrar el navegador; el backend agrega la ventana de inactividad de 60 min) y lo propaga por `axios.defaults`, igual que `utils/entorno.js` con el entorno — las llamadas con `fetch()` nativo sí necesitan `headerSesion()` a mano, junto a `headerEntorno()`/`headerApiKey()`. Un interceptor de axios devuelve al login ante cualquier 401 que no venga de `/auth/login` ni `/auth/yo`. No se usa cookie porque el SPA y el backend son servicios distintos de Render: sería cookie de terceros y Safari la bloquea.

Screens (`src/screens/`), each a route in the router (`react-router-dom` v7, no code-splitting):
- `IngresoScreen` (`/`) — intake of new solicitudes.
- `DashboardScreen` (`/dashboard`) — macro control view of OTs/solicitudes.
- `TratamientoScreen` (`/tratamiento`) — builds out an OT's tasks/materials/logistics, quotation PDF generation (`jspdf` + `jspdf-autotable` + `html2canvas`), triggers supervisor email / WhatsApp share.
- `GanttScreen` (`/gantt`) — scheduling view using `calendarios`/`recursos` to compute available hours per day (`obtenerHorasParaDia`, defined in `App.jsx`).
- `RecursosScreen` (`/recursos`) — CRUD for personnel, equipment, supplies, puestos, calendarios, plantillas (the "admin" screen — currently open in the IDE).
- `ReporteTerreno` (`/reporte`) — field report view for a specific OT (`?id=`), used for photo/comment reporting.

**Modo guía** (`src/guia/`, botón «Guía del sistema» al pie del menú): un recorrido de diez pasos que sigue el flujo del negocio —solicitud → aprobación → armado de la OT → programación → terreno → los catálogos que lo alimentan— señalando elementos reales de cada pantalla. La primera visita ofrece un aviso chico abajo a la derecha en vez de abrirlo solo: secuestrarle la pantalla a quien entró a trabajar sería al revés de lo que se busca. **Tres decisiones con prueba.** (1) **Señala y no toca**: ningún paso ejecuta nada, por eso se puede correr sobre la base real de un taller que está trabajando y no solo sobre la demo — `pasos.test.js` rechaza cualquier clave que no sea texto, así que un `alEntrar: () => …` no entra sin que alguien lo decida a propósito. (2) **El ancla es un `data-guia="…"`, nunca un selector CSS**: un `.card:nth-child(2)` se rompe en silencio al reordenar una pantalla y el síntoma aparece recién mientras se le muestra el sistema a un cliente; hay prueba de que cada ancla del guion existe en el código **una sola vez** (dos iguales harían que el foco caiga en la que encuentre primero el navegador) y de que no queden anclas huérfanas. (3) **Si el ancla no está en pantalla, el paso sale centrado y sin foco**: pasa de verdad —una tabla vacía no tiene filas— y apuntar a la posición equivocada le dice a quien mira que el sistema está roto. El guion vive en `pasos.js`, separado del motor (`Guia.jsx`), porque es lo que se va a editar cuando cambie la forma de contar el producto. El foco se dibuja con **un solo div y una sombra de 9999px**, que oscurece todo menos ese rectángulo sin recortes SVG ni cuatro paneles que calzar. Recorriendo los diez pasos en un navegador de verdad se encontró que **el paso de la OT no podía llevar a `/tratamiento`**: esa pantalla solo existe con una OT elegida y entrar directo muestra «No hay datos», así que ese paso se queda en el panel. De paso quedó visto que **la app no tiene error boundary**: `TableroSupervisoresScreen` hace `datos.supervisores.length` sin guarda, y con una respuesta de otra forma la pantalla entera queda en blanco —la guía incluida, porque vive en el mismo árbol—.

No CSS framework/UI kit: styling is a mix of inline `style` objects (see `styles` const at the bottom of `App.jsx`) and plain CSS files (`App.css`, `index.css`, `screens/index.css`). `useIsMobile` (`src/hooks/useIsMobile.js`) is the only shared hook, used to switch the nav between desktop links and a hamburger menu at a 768px breakpoint.

WhatsApp integration is a plain `wa.me` deep link built client-side (`enviarASupervisor` in `App.jsx`), not an API integration.

## Conventions to follow

- **Decir siempre dónde conviene hacer el cambio.** Hay dos superficies: una **sesión de nube** (claude.ai/code, contenedor efímero con un clon fresco, sin acceso al navegador, al `.env` ni a la Mongo de quien trabaja) y **Claude en VS Code** (local, con los archivos abiertos, el `.env`, la base real y la app corriendo). No comparten conversación: lo único que viaja entre las dos es el repositorio, así que **el *por qué* de cada decisión va en los mensajes de commit, en el cuerpo del PR y en `docs/`**, no en el chat. Al recibir un pedido de trabajo, **la primera línea de la respuesta dice en qué superficie conviene hacerlo y por qué, en una frase**. El criterio:
  - **Necesita ver la app corriendo, la base real o el `.env` → VS Code.** Pantallas, usabilidad, "esto se ve mal", el Gantt que no cuadra, cualquier cosa cuyo ciclo sea *cambio → mirar el navegador → ajustar*. Desde la nube eso es adivinar.
  - **Se verifica con pruebas y lectura de código → nube.** Backend, pruebas, documentación, refactors, cambios que terminan en un PR con su explicación escrita.
  - **No necesita Claude:** mirar el log de Render, revisar Brevo, confirmar que se puede entrar. Eso lo hace la persona y trae el resultado.
  - **Una sola superficie por rama a la vez**, o los cambios se chocan. Y `git push` antes de cambiar de lado: es el único canal entre las dos, y el contenedor de la nube se recicla sin avisar.

- **Multi-taller (SaaS)** — ver [`docs/multi-taller.md`](docs/multi-taller.md). Resumen: una base por taller (no un campo `tallerId`), porque los 291 usos de `req.db` ya resuelven la conexión en un solo punto (`middlewares/entorno.js`) y los 11 índices únicos globales siguen funcionando por base. **Regla que no se negocia**: el taller sale de `req.usuario`, nunca del header `X-Entorno` ni de `?entorno=` — hoy el cliente los elige, lo que es inofensivo entre la producción y la demo del mismo dueño y sería una fuga de datos si eligiera de qué cliente son. **Etapas 1, 2, 3, 4 y 5 hechas** (la 4, salvo que la PWA deje de mandar el entorno; la 5, salvo la baja de un cliente y la demo nocturna). Etapa 1: `config/talleres.js`, `Usuario.tallerId` (sin default — las cuentas anteriores se resuelven como del taller por defecto), y el token de sesión con prefijo `<taller>.<token>` que rompe la dependencia circular *para saber el taller hay que leer la sesión, que vive dentro de la base del taller*. Etapa 2: `models/Taller.js` en la base de control, el registro en memoria de `config/conexiones.js` (conexiones de producción bajo demanda, pool acotado, demo compartida) y `/api/talleres`. Etapa 3 (el backend): el alta devuelve **una sola vez** un enlace de instalación `SPA_URL/instalar?taller=<slug>&clave=<token>` —en la base queda solo su hash—, y `POST /api/instalacion` con `taller` instala contra **la base de ese taller**, construyendo antes sus índices. La pantalla ya está: `InstalacionScreen` aparece sola cuando `GET /auth/yo` responde `requiereInstalacion` —antes del router, así que sirve en cualquier ruta, `/instalar` incluida— y lee la clave de `?clave=` **una sola vez, al cargar el módulo**: con la clave en el enlace el campo **no se muestra** (un campo ya lleno que el cliente no puede corregir solo invita a borrarlo) y la clave se **borra de la barra de direcciones** con `replaceState` —es una credencial: ahí queda a la vista de quien mire la pantalla, se va en el `Referer` y se cuela en una captura—, conservando `?taller=`, que es ruteo y hay que recordarlo. Por eso se lee en el módulo y no en cada render: después de limpiarla, una segunda lectura daría vacío. Si esa clave está vencida el cliente no tiene nada que escribir para arreglarlo, así que el error le dice que pida un enlace nuevo en vez de dejarlo mirando una pared. **Lo que falta es hacerlo una vez de punta a punta con un cliente de verdad**; el backend está cubierto por `test/instalacionTaller.test.js`, el navegador no. **Lo que pasa antes de tener sesión** (entrar, recuperar, activar) resuelve el taller con `conexionPedida` a partir de `X-Taller`/`?taller=` — pista, no credencial; ver el bullet de arquitectura. **El prefijo es ruteo, no autenticación**: solo elige en qué base buscar el token, que igual tiene que existir ahí, y `middlewares/sesion.js` además verifica que el usuario pertenezca a ese taller. Un token sin punto es una sesión anterior al cambio y se entiende del taller por defecto. Etapa 4: **el token de persona de la PWA Operativa y el del portal del cliente también llevan prefijo**, y `entorno.js` mira las dos credenciales (`Authorization: Bearer` y `?token=`) en vez de solo la primera. Antes solo miraba la sesión de escritorio, así que toda llamada de las PWAs caía en la base del taller por defecto: con un cliente no se notaba, con dos la gente de terreno del segundo y sus clientes no podían entrar mientras la app de escritorio andaba bien, sin un solo error que lo explicara. `tokenMovilDeLaRequest` y `sinPrefijo` viven en `utils/tokens.js` porque los necesitan los dos middlewares. **Las PWAs no se tocaron y no hay que redesplegarlas**: guardan el token como cadena opaca y lo devuelven tal cual, y los ya instalados —sin prefijo— siguen resolviendo al taller por defecto, que es donde de verdad están.
- **Toda etapa tiene vuelta atrás** — principio rector de producto, ver [`docs/principio-vuelta-atras.md`](docs/principio-vuelta-atras.md). Antes de agregar un paso que cierra algo (aprobar, aceptar, finalizar, enviar), definir explícitamente cómo se deshace y hasta cuándo. Cuatro reglas: el corte lo decide quien revisa, no quien ejecuta; la vuelta atrás va donde se detecta el problema; deshacer también revierte los efectos (reservas de stock/equipos, envíos, copias congeladas), no solo el `estado`; y toda ida y vuelta queda en `OT.bitacora`. Ese documento tiene además el mapa de qué etapa se puede deshacer hoy y cuál no.
- Backend is CommonJS (`require`/`module.exports`); frontend is ESM (`import`/`export`). Don't mix.
- Domain language throughout the codebase (variables, model fields, routes, UI copy) is Spanish — match it in new code rather than introducing English identifiers.
- Mongoose models guard against recompilation with `mongoose.models.X || mongoose.model('X', schema)` in some files (`OT`, `Solicitud`, `Plantilla`) but not others (`Recurso`, `Calendario`, `EquiposHerramientas`, `Puesto`, `Suministro`) — copy the pattern of the file you're editing rather than "fixing" inconsistently across the codebase in an unrelated change.
- Controllers return raw Mongoose documents/plain JSON with ad hoc shapes (sometimes the doc directly, sometimes `{ ot: doc }`, `{ mensaje }`, `{ success, ... }`) — check the specific controller/frontend caller before assuming a response shape.
- IDs from Mongo are matched frontend-side with `String(a) === String(b)` throughout (ObjectId vs string comparisons) — follow this pattern rather than relying on `===` directly on IDs.
